# 08. LLM-as-a-judge によるプロンプト・出力品質評価

RAGアプリケーションのようにLLMが自然文を生成するシステムでは、「正解が1つに定まらない」出力の品質をどう評価するかが課題になる。本章では、LLM自身を評価者（judge）として使い、プロンプト設計の優劣を定量的に比較する手法と、実践を通じて得た設計上の教訓をまとめる。

実装例は AI-Recipe-Book（`search-assist` 機能のプロンプト改善）を題材にしている。プロジェクト固有の実験過程・生データは該当リポジトリの `docs/appendix_roadmap_phase3_llm_as_judge/` を参照。本章では、他のプロジェクトにも転用できる一般的な設計知識として整理する。

---

## 1. LLM-as-a-judgeとは何か、なぜ必要か

### 課題

RAGASのPrecision@k/Recall@k（本GrepAIの [05_evaluation_and_monitoring](../05_evaluation_and_monitoring/) 参照）は「検索が正しい文書を引けているか」を評価できるが、「**LLMが生成した最終的な回答文の質**」は評価できない。回答文の品質（分かりやすさ、過不足のなさ、指示への忠実性）は数値的な正解ラベルを用意しにくく、人手評価はコストが高く再現性にも欠ける。

### 解決アプローチ

評価対象のLLMとは別に、**もう1つのLLM呼び出しを「審査員（judge）」として使い**、複数の候補回答を比較・採点させる。これにより、以下が低コストで実現できる。

- プロンプトのバージョンA/Bのどちらが優れているかを、多数のテストケースに対して機械的に判定できる
- 判定理由（reasoning）をLLMに言語化させることで、**勝敗だけでなく「なぜ」を分析材料にできる**（後述の実践例で、この点が改善の発見に直結した）

### 限界（過信してはいけない点）

- judge自体もLLMであり、判定にブレや偏りが生じうる
- 「良い回答」の基準（評価軸）を人間が事前に設計する必要があり、軸の設計が甘いと評価そのものが的外れになる
- 商用LLM APIを使う場合、judgeの温度設定や試行回数によっては、出力のランダム性が結果に混入する（3節・4節で詳述）

---

## 2. 評価軸の設計

「どちらが良いか」を1軸で判定させると、判定理由が曖昧になりやすい。実践では以下5軸に分解し、各1〜5点で採点させた上で、最終的な勝者（A/B/tie）を判定させる構成にした。

| 軸 | 何を測るか |
|---|---|
| 関連性（relevance） | ユーザーの質問の意図に的確に答えているか |
| 忠実性（faithfulness） | 与えられたコンテキストの範囲内で回答し、存在しない情報を捏造していないか |
| 網羅性（completeness） | コンテキストに含まれる妥当な情報を過不足なく扱えているか（省きすぎ・詰め込みすぎの両方を減点対象にする） |
| フォーマット遵守（format_compliance） | 指定された出力形式に従っているか |
| 有用性（usefulness） | ユーザーが次の行動に移せる、実用的な回答になっているか |

**ポイント**：評価したいシナリオが複数のカテゴリにまたがる場合（例：「情報が0件の時」「複数候補がある時」「曖昧な質問の時」）、カテゴリごとに「このケースで最優先すべき軸」をjudgeへのプロンプトに明示すると、判定のブレが減る。5軸を固定した上で、カテゴリ固有の重みづけは自由記述のプロンプト文で伝える設計が、出力フォーマットの安定性と柔軟性を両立しやすい。

## 3. バイアス排除の設計

judgeに複数の候補を見せる際、**提示順序がそのまま判定結果に影響しうる**（先に提示した方を無意識に高く評価する傾向が知られている）。対策は単純だが効果的である。

1. 候補の提示順を**毎回ランダムに入れ替える**
2. judgeには「どちらがA、どちらがBか」という**ラベルを一切見せない**（「回答1」「回答2」等の中立的な呼び方にする）
3. 判定が返ってきた後、コード側で「回答1」→実際のラベル（A/B/ハイブリッド等）に**逆マッピングし直す**

```python
candidates = [("hybrid", response_hybrid), ("prompt_A", response_a), ("prompt_B", response_b)]
random.shuffle(candidates)
label_by_slot = {str(i + 1): candidates[i][0] for i in range(len(candidates))}
# judgeには "回答1"〜"回答N" として提示し、結果を label_by_slot で実際のラベルに戻す
```

3候補以上の比較も、2択の判定を複数回繰り返すより、**1回のjudge呼び出しで済ませる方がAPIコストを抑えられる**（実践では3者比較を1回のjudgeプロンプトで行った）。

## 4. 実践から得た教訓

### 4.1 プロンプト設計に「絶対解」はない。状況に応じたハイブリッド設計が有効な場合がある

「追加の指示を入れたプロンプト」が常に優れているとは限らない。実践では、検索結果の状態（1件に絞れているか、複数候補が拮抗しているか）によって最適なプロンプトが変わることが定量的に確認できた。

これに対する解決策は「A/Bどちらか一方を選ぶ」ではなく、**機械的に判定できる条件（件数・スコア差）で一次分岐し、判定が難しいケースにのみLLM自身に意図分類をもう1回行わせて二次分岐する**という設計だった。全てのケースで判定コールを挟むと無駄なコストが発生するため、「一次分岐で振り分けられない場合にのみ、追加のLLM呼び出しを行う」というコスト意識のある設計が実務的に有効である。

### 4.2 指示の「一律適用」は副作用を生む。条件付き適用が必要になることがある

改善プロンプトに含めた「DBに情報がない場合は断定しない」という指示は、**聞かれてもいない場面でまで律儀に発動し**、不要な注記として有用性スコアを下げる副作用を引き起こした。judgeのreasoningを読み込むことでこの副作用を特定し、「質問文に関連キーワードが含まれる場合のみ、その指示を動的に注入する」という条件付き設計に修正することで解消できた。

**教訓**：プロンプトの指示は「多く盛り込むほど良い」わけではなく、それぞれの指示が**どんな条件で発動すべきかを個別に設計する**必要がある。

### 4.3 judgeのreasoningは、勝敗の数字より価値がある情報を含む

単に「Aが3勝、Bが4勝」という集計だけでは、次にどう改善すべきかは分からない。**各判定のreasoning（判定理由）を読み込むことで、「なぜBが負けたのか」という具体的な原因（4.2の副作用など）を特定できた。** LLM-as-a-judgeを使う際は、勝敗のスコアだけでなく、reasoningを分析対象として活用する設計にすべきである。

### 4.4 商用LLM APIでの評価には、固有の制約が伴う

ローカルで動かす自作モデルの評価とは異なり、商用APIを使った評価には以下の制約がある。

- **無料枠の制限**：分単位ではなく「1日あたり」のリクエスト上限が設定されている場合がある。上限に達した場合は待っても回復しないため、エラーメッセージから上限の種類（分単位か日単位か）を判別し、日単位の場合は即座にリトライを諦めて処理を中断する設計にすべき
- **出力のランダム性**：`temperature`パラメータを下げることで出力のブレはある程度抑えられるが、完全にはゼロにならない。実験のスコープとして「各ケース1試行のみであり、複数回試行による統計的検証は行っていない」という限界を、正直に記録に残すべきである
- **モデルの非恒久性**：基盤モデルは提供企業側の裁量で更新・非推奨化されうる（実際に本プロジェクトでは`gemini-2.0-flash`の廃止を経験した）。評価結果は「その時点のスナップショット」として扱い、**モデル更新時に低コストで再実行できる評価スクリプト（ハーネス）として設計しておく**ことで、この制約に対処できる
