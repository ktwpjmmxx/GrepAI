# 06. 評価・モニタリング

RAGやLLMを使ったアプリケーションは「動いているように見える」ことと「正しく動いている」ことが別物になりやすい。本章では、検索（Retrieval）と生成（Generation）それぞれの評価指標の基礎を整理した上で、実際に自分のポートフォリオプロジェクト（AI-Recipe-Book）で発見した実運用上の問題を、ケーススタディとしてまとめる。

---

## 1. RAGのどこを測るべきか

RAGパイプラインは大きく2段階に分かれ、それぞれで評価すべきことが違う。

```
[ユーザーの質問]
      ↓
① Retrieval（検索）: 質問に関連するチャンクをVector DBから取り出す
      ↓
② Augmented Generation（生成）: 取り出したチャンクを元にLLMが回答を生成する
      ↓
[最終回答]
```

- **①の評価**：そもそも「正しい情報」を検索できているか（検索の質）
- **②の評価**：検索した情報を元に、LLMが正確な回答を作れているか（生成の質。ハルシネーションしていないか）

この2つを分けて考えられることが評価設計の出発点になる。混同していると、精度が低いときに検索が悪いのか生成が悪いのか切り分けられない。

---

## 2. 検索（Retrieval）の指標

| 指標 | 意味 | 直感的な言い方 |
|---|---|---|
| **Precision@k** | 上位k件のうち、本当に関連していた割合 | 「検索結果のうち何割が当たりだったか」 |
| **Recall@k** | 本当は関連するチャンク全体のうち、上位k件で拾えた割合 | 「拾うべき正解のうち何割拾えたか」 |
| **MRR（Mean Reciprocal Rank）** | 最初に正解が出てきた順位の逆数の平均 | 「一番欲しい答えがどれだけ上に来たか」 |

具体例（レシピ検索アプリで「鶏肉 唐揚げ 下味」というクエリを投げたとき）：

- Vector DBに関連するチャンクが本当は4個ある
- 上位5件の検索結果のうち3個が本当に関連していた
- → Precision@5 = 3/5 = 0.6
- → Recall@5 = 3/4 = 0.75

---

## 3. 生成（Generation）の指標：RAGASの主要4指標

RAGAS（RAG Assessment）というライブラリを使うと、生成の質を自動計算できる。

| 指標 | 何を測るか |
|---|---|
| **Faithfulness（忠実性）** | 生成された回答が、検索されたチャンクの内容に基づいているか（ハルシネーションしていないか） |
| **Answer Relevancy（回答の関連性）** | 生成された回答が、ユーザーの質問にちゃんと答えているか |
| **Context Precision（文脈の精度）** | 検索されたチャンクのうち、実際に回答に必要だったものの割合が高いか |
| **Context Recall（文脈の再現率）** | 正解に必要な情報が、検索されたチャンクにちゃんと含まれていたか |

イメージで覚えるなら、Faithfulnessは「回答が資料に沿っているか」、Context Precision/Recallは「そもそも良い資料を持ってこれたか」。前者が低ければ生成（プロンプト・LLM側）の問題、後者が低ければ検索（チャンクサイズ・埋め込みモデル・閾値）側の問題だと切り分けられる。

---

## 4. 評価用データセットの作り方

RAGASは「質問」「正解（ground truth）」のペアがないと評価できない。既存のベンチマークは自分のドメインデータには使えないため、自分で作る必要がある。

質問の種類にバリエーションを持たせることが重要：

- 単純な検索質問（例：「鶏肉を使った煮物のレシピは？」）
- 曖昧な質問（例：「あっさりした夕飯のメニュー」）
- 複数条件の質問（例：「30分以内で作れる、卵を使わない朝食」）
- 存在しない情報を聞く質問（ハルシネーション検出用。例：「牛肉の刺身レシピは？」）

最後の「存在しない情報を聞く質問」は特に重要。LLMが「ありません」と正直に答えられるか、それとも作り話をするかで、Faithfulnessの実力が分かる。

## 5. 実践例：AI-Recipe-Bookでの埋め込みモデル未設定問題

理論を学んだ後、実際に自分のポートフォリオプロジェクト（[AI-Recipe-Book](https://github.com/ktwpjmmxx/AI-Recipe-Book)）のRAG機能を検証したところ、実運用上の問題を発見した。

### 発見の経緯

1. 検索assist機能を実際に触って動作確認する中で、実在するレシピ名を含む質問（「ナシゴレンのレシピを教えて」）でも検索結果が0件になる事象を発見
2. ChromaDBのコレクションを直接操作し、フィルター適用前の生の距離（コサイン距離）を確認したところ、全質問・全候補が0.85〜1.09という狭い範囲に密集しており、関連度閾値（0.85）を超えて全て除外されていたと判明
3. 質問文にレシピ名がそのまま含まれるのに、そのレシピ自体が検索結果の上位に来ないという逆転現象も確認し、単なる閾値設定のミスではなく、埋め込みモデル自体が意味的な近さを正しく計算できていない可能性を疑った
4. 原因は、ChromaDBの`get_or_create_collection()`で埋め込み関数（`embedding_function`）を明示的に指定しておらず、ChromaDBのデフォルト埋め込みモデル（英語中心、日本語の意味理解に弱い）が使われていたことだった

### 学んだこと

- 「動いているように見える（0件でもエラーにならない）」ことと「正しく動いている」ことは別物である
- 閾値のチューニングだけでは直せない問題がある。閾値は「距離のスケールが妥当である」ことが前提であり、スケール自体がおかしい場合はまず埋め込みモデルを疑う必要がある
- フィルター適用後の結果だけを見ていても原因は分からない。フィルター適用前の生の距離を確認することで、初めて「閾値が厳しすぎる」のか「そもそも埋め込みが機能していない」のかを切り分けられる
- Before/Afterを同一の質問セット（表記ゆれ・口語表現・存在しない情報などのカテゴリを含む）で計測し、数値で比較することで、改善を客観的に主張できる

### 対応と結果

Gemini `gemini-embedding-001`に変更し、登録用（`RETRIEVAL_DOCUMENT`）と検索クエリ用（`RETRIEVAL_QUERY`）でtask_typeを使い分けた上で、同じ8質問で再計測した。

質問文にレシピ名を含む基準ケースで、正解レシピの順位が4位→1位に改善し、全体の距離分布も0.89〜1.09という区別の付かない範囲から、0.19〜0.42という意味的な区別が可能な範囲に変化した。これに伴い、それまで実質的に機能していなかった関連度閾値も0.85から0.35に再調整した。

詳細な計測データ・調査プロセス・検証スクリプトは[AI-Recipe-Book/docs/Version_5.3](https://github.com/ktwpjmmxx/AI-Recipe-Book/tree/main/docs/Version_5.3)を参照。

### この経験から得た、他のプロジェクトにも応用できる教訓

1. ベクトルDBの埋め込み関数は、ライブラリのデフォルトに頼らず必ず明示的に指定する
2. 閾値の調整に着手する前に、まず生の距離分布を確認し、そもそも比較可能なスケールになっているかを検証する
3. 「質問文にキーワードが完全一致するのに検索結果に出てこない」という現象は、埋め込みモデルの信頼性を疑う強いシグナルになる
4. 副次的な発見（今回はレシピの重複登録、テストのベクトルDB隔離漏れ）も見逃さず、都度切り分けて対応する
